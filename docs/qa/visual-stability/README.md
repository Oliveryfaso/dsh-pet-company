## 100fps 的实际含义

31 段文件为 640×360 VP9 alpha，容器帧率100fps。它使用10ms刻度重复已有源帧，精确表达原 SPEC 的帧保持时长，**没有生成中间姿态**。

九类原动作平均仅5.45–7.55个逻辑帧/秒；最短单帧保持110ms，局部更新最快约9.09次/秒。增加重复帧不等于插帧，也不能消除源画本身的姿态跳变。100fps可能增加软件解码负担，但本轮没有测量其实际CPU、GPU耗用，不能把它直接当作唯一闪烁原因。

31 段包含27个源动作、3个 care 别名和橙色 source-idle 别名。银白/海蓝 care 对应 waving；橙色 care 现对应 review，不再对应旧 waving。每个文件都按实际源动作与此前已完整解码校验的参照文件逐字节比对，结果全部相同；因此可关联此前“每段保持期间像素不变、总帧数及时长正确”的验证。`existing-31-clips.json`明确区分新头信息与复用的旧解码证据，本轮没有再做完整解码。

## 循环与播放器证据应分开

默认待机首末轮廓重叠率分别为银白0.9431、橙色0.8161、海蓝0.9621（alpha≥16）。这只是轮廓连续性指标，不代表主观流畅性评分；橙色 review 首末变化更明显，不能声称三套源素材完全无接缝。

修复前播放器的无界面 VM 复现显示：单一 idle 初始加载加三次 ended，会重新 load 四次并交替 A/B。两层同时0.18秒交叉淡入时，两个原本不透明像素在中点的理论合成 alpha 为0.75，会周期性变淡。当前证据并未证明解码器实际输出透明空帧。原55%垂直 squash 在已开启 presentation 的新代码里已有拦截，不能把当前橙色扁姿态直接归咎该旧动画。

最小修复优先处理同素材循环与切层可见性，再验收真实播放。若仍有源帧跳变或解码压力，再单独评估稳定选帧、温和重定时或保留精确时间戳的 VFR；这些是后续候选，未在本轮实施。

## 播放器候选回归

已加入仅对 presentation 启用的候选：固定单待机采用原生 loop；新动作先保留旧帧，待新视频帧可提交时原子换层，取消交叉淡化；过期/失败/抢占/卸载均取消监听、帧回调与计时器。真实提交记录与加载请求代际分离，避免旧 ended 抢占新动作，也避免新加载失败后旧动画永久失去结束权限。工作状态与热配置路径保留原有状态语义。未启用 presentation 的宠物保留旧播放分支。

直接执行候选源码的 18 项 helper mock、20 项 Web mock 已通过，且测试输入与官方运行时构建一致。

## 真实单宠复测

在内存恢复 normal/raw1 后，使用同一隔离 Profile 与已批准的官方 Electron 43.3.0，按橙色、银白、海蓝顺序运行，每次仅一只，阶段结束即停止本任务进程。三只均通过真实原生界面触发点击和显式关怀，并查看实际窗口像素、云朵、回到待机；蓝色还验证了关闭气泡。橙色点击和关怀保持阅读比例，采样中未复现空帧或周期变淡。此前保存的喝水92分钟在主窗口重启后恢复。

这属于有界截图采样，不是连续逐帧录制，也不能证明长期零闪烁。220ms轻回弹完整曲线、短拖动的屏幕位移、OS跨应用焦点、透明区域点击穿透和物理多屏/DPR仍未完整验收；不据白底窗口截图推导整个桌面合成透明性。源动画仍有约6帧/秒的分帧感，本次没有插帧。明细与局限见 [真实 helper 结果](native-helper-results.json)。
